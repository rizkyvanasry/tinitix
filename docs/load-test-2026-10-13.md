## Lingkungan dan target

Satu proses `next start` lokal mengakses PostgreSQL staging melalui jaringan dari mesin penguji. Data memakai schema acak tersendiri; compute database tetap berbagi instance staging. Pool aplikasi tetap 3 koneksi. Ada 10 organisasi, 10 event, dan 500 pesanan paid per event (5.000 total). Hingga 50 tab dashboard tersebar di 10 akun EO, bukan 50 tenant berbeda. Seluruh pembelian diarahkan ke satu event untuk menguji perebutan stok.

Target: p95 dashboard <=1 detik; p95 tiap langkah checkout <=2 detik; p95 perjalanan checkout <=10 detik; error HTTP <1%; tidak ada polling terlewat; stok/revenue cocok dengan SQL; tidak ada overselling. Warmup tidak dihitung.

Sampling `pg_stat_activity` sekitar satu detik, difilter untuk koneksi aplikasi pengujian; koneksi fixture dan observer dikecualikan. Nilai aktif nol berarti tidak tertangkap saat sampling, bukan tidak ada query. Sebagian besar sampel menunjukkan `ClientRead`: PostgreSQL menunggu perintah berikutnya dari aplikasi. Ini tidak menunjukkan CPU database penuh.

20 round-trip `SELECT 1` sebelum beban: rata-rata **60.8 ms**, p95 **66.5 ms**. Probe tambahan pada percobaan awal menjalankan `EXPLAIN ANALYZE` untuk agregasi harian: execution **3.527 ms**, planning **1.047 ms**, 3.111 shared buffer hits, tanpa shared reads/temp spill. Ini satu query pada sekitar 500 pesanan/event, bukan total waktu endpoint atau benchmark dataset besar.

Pembacaan kode menunjukkan endpoint live mengautentikasi dua kali dan menjalankan sekitar 13 statement termasuk BEGIN/SET/COMMIT. Dengan round-trip sekitar 61 ms, perjalanan serial ke database berkontribusi besar sebelum antrean. Pool tiga koneksi dan transaksi panjang merupakan kandidat bottleneck. Waktu tunggu pool belum diinstrumentasi langsung; kesimpulan ini adalah diagnosis berdasarkan kode dan pengukuran, bukan pengukuran CPU/queue yang lengkap.

CPU, RAM, IOPS dan limit koneksi instance PostgreSQL belum diukur karena monitoring provider tidak tersedia dalam tes ini. Statistik insert/update/index scan per tabel dicatat dalam JSON; nilainya kumulatif sejak fixture dibuat.

## Konsistensi setelah transaksi selesai

- Rekonsiliasi seluruh tahap: **LULUS**. Revenue dan jumlah order paid event yang menerima pembelian cocok dengan SQL; ketersediaan stok cocok dengan reservasi.
- Tidak ada kategori oversold pada seluruh event yang diuji.
- Sebelum rekonsiliasi, harness menunggu lima observasi berturut-turut tanpa transaksi aktif. Semua tahap berhasil mencapai kondisi tersebut.
- Klien timeout dapat terjadi sementara transaksi tetap berhasil di server. Karena itu, timeout tidak sama dengan pembayaran gagal. Percobaan awal membandingkan data saat transaksi masih berjalan; hasil rekonsiliasi tersebut digantikan oleh pengukuran utama ini.
- Schema pengujian sudah dihapus; tidak ada email nyata dikirim dan tidak ada pembayaran nyata dibuat.

## Tindakan berikutnya

1. Ulangi pengukuran dari runtime/region yang sama dengan deployment, menggunakan database uji tersendiri. Hasil lokal ini tidak bisa dijadikan batas kapasitas Vercel.
2. Kurangi perjalanan SQL serial dan autentikasi ganda pada endpoint live. Pertimbangkan agregasi snapshot pendek per event/tenant untuk mengurangi query berulang, dengan invalidasi saat transaksi berubah.
3. Ukur waktu antre pool serta koneksi total lintas instance sebelum mengubah ukuran pool; menambah koneksi tanpa data dapat memindahkan bottleneck ke database.
4. Pertahankan pencegahan request overlap; tambahkan jitter/backoff saat lambat. Retest target 50/10 setelah perbaikan, lalu uji stabil 30 menit dan burst checkout/polling serentak.

Tidak ada perubahan perilaku aplikasi dalam pekerjaan ini. Yang ditambahkan adalah harness, perintah `npm run test:load`, panduan, dan hasil pengukuran. Lihat [cara mengulang tes](load-testing.md) dan [data mentah](load-test-2026-10-13.json).
